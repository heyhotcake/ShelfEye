Top risks to address now (months‑to‑years uptime)

Long HTTP requests can be killed by default Node timeouts
Evidence: Calibration/preview/validation routes spawn Python and can run for minutes, but I see only per‑process timeouts (e.g., server/scheduler.ts Lines 600–706, 653–690; server/routes.ts Lines 1276–1283, 3646–3683). No global HTTP server requestTimeout/headersTimeout/keepAliveTimeout or per‑route res.setTimeout. If the server takes >2 minutes without sending data, Node may terminate the socket before your Python finishes.

Fix (minimal, per‑route): set a generous response timeout at the start of long routes.
Example for calibration, verify-positions, rectified-preview, validation:
Typescript
// inside each long-running handler, at the top
res.setTimeout(12 * 60 * 1000); // 12 minutes to exceed CAPTURE_TIMEOUT_MS safely

Fix (server-wide, preferred): configure the HTTP server timeouts once to match your CAPTURE_TIMEOUT_MS (10m) + headroom.
Typescript
// server/index.ts
import http from 'http';
const httpServer = http.createServer(app);
httpServer.requestTimeout = 12 * 60 * 1000;
httpServer.headersTimeout = 13 * 60 * 1000;
httpServer.keepAliveTimeout = 75_000;
httpServer.listen(port, '0.0.0.0', () => console.log('listening'));

Alert retry queue is not durable; restarts can reprocess or lose alerts
Evidence: Comments warn duplicates and divergence on restart, with an in‑flight buffer heuristic (server/services/alert-queue.ts Lines 52‑56, 61‑65). No persistence hooks found (“persist|restore” search returned none).
Impact: Power loss or systemd restart risks duplicate emails/rows or silent loss if state diverges.
Fix (DB-backed queue, minimal design):
Schema (Drizzle):
Typescript
// shared/queue-schema.ts
export const alertQueue = pgTable('alert_queue', {
id: varchar('id').primaryKey(),
type: text('type').notNull(), // 'email' | 'sheets'
payload: json('payload').notNull(),
retries: integer('retries').notNull().default(0),
nextRetryAt: timestamp('next_retry_at').notNull(),
createdAt: timestamp('created_at').default(sqlnow()),
status: text('status').notNull().default('pending'), // pending|processing|done|dead
lastError: text('last_error'),
});
On enqueue: insert row; on retry cycle: SELECT … FOR UPDATE SKIP LOCKED where status IN ('pending','processing') and next_retry_at <= now(); update status='processing' with heartbeat; on success set status='done'; on expiry set status='dead'.
On boot: requeue any status='processing' older than, e.g., 10 minutes.
Unscoped process killing can terminate unrelated processes
Evidence: pkill/fuser used broadly (server/routes.ts Lines 521–538) to clear camera contention.
Impact: Risk of killing non‑ShelfEye Python or other services on the Pi.
Fix: Track PIDs you spawn and terminate by PID/purpose via the existing SubprocessManager.
Typescript
// server/subprocess-manager.ts
killByPurpose(purpose: string) {
for (const [pid, meta] of this.tracked) {
if (meta.purpose === purpose) try { process.kill(pid, 'SIGKILL'); } catch {}
}
}
// server/routes.ts (replace pkill/fuser block)
subprocessManager.killByPurpose('aruco_calibrator');
subprocessManager.killByPurpose('camera_preview');
subprocessManager.killByPurpose('validate_slot_qrs');
// for v4l2 contention, kill only tracked PIDs that opened /dev/video* per your tracking

Security and abuse hardening (LAN today, but safe defaults)

No security headers, CORS discipline, or body/rate limits
Evidence: No helmet/cors wiring; no express.json limit; no limiter (search returned none).
Fix (safe defaults):
Typescript
import helmet from 'helmet';
import cors from 'cors';
import rateLimit from 'express-rate-limit';
app.use(helmet({
frameguard: { action: 'deny' },
hsts: false, // Pi LAN

Disk usage sentinel
Evidence: No periodic disk check; SD fill is a classic Pi killer.
Fix: Add a tiny script and a systemd timer to log error and flip the alert LED if / or /home exceeds, say, 85%.
Bash
scripts/check-disk-usage.sh
THRESH=85
for mp in / /home; do
used=$(df -P "$mp" | awk 'NR==2{print $5}' | tr -d '%')
if [ "$used" -ge "$THRESH" ]; then
echo "[Disk] 
m
p
a
t
{used}% used" | systemd-cat -t shelfeye -p err
curl -m 2 -sS http://localhost:5000/api/alerts/disk-full || true
fi
done
Then add a systemd timer (hourly). Also keep journald/logrotate retention caps as documented.

Fix: Ensure node‑cron uses the configured timezone when scheduling jobs:
