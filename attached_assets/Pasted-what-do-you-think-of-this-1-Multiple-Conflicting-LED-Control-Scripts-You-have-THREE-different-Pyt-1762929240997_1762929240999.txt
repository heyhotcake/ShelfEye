1. Multiple Conflicting LED Control Scripts
You have THREE different Python scripts trying to control the same LED strip:

unified_led_controller.py (supposed to be the main one with priority management)
gpio_controller.py (has its own WS2812 control)
alert_led.py (standalone alert controller)
This is causing conflicts when different parts of your system use different scripts.

2. Resource Contention on DMA Channel
The WS2812 library uses DMA channel 10, but multiple processes are trying to access it simultaneously without proper cleanup.

3. Zombie Processes
When LED processes crash or get stuck, they hold onto the DMA channel, preventing new processes from working.

5. Fix Permissions
#!/bin/bash

# Create systemd service for LED manager
sudo tee /etc/systemd/system/led-manager.service > /dev/null <<EOF
[Unit]
Description=ShelfEye LED Manager Service
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/home/naniwa/ShelfEye
ExecStart=/usr/bin/python3 /home/naniwa/ShelfEye/python/led_manager_service.py
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

# Enable and start service
sudo systemctl daemon-reload
sudo systemctl enable led-manager.service
sudo systemctl restart led-manager.service

# Set permissions
sudo chmod 666 /tmp/led_control_pipe 2>/dev/null || true
sudo chmod 666 /tmp/led_state.json 2>/dev/null || true

echo "LED Manager Service installed and started"

Key Improvements:
Single Process: Only one process controls the LED strip, eliminating DMA conflicts
Priority System: Commands have priorities, preventing low-priority commands from interrupting alerts
State Persistence: LED state is saved and can be queried
Automatic Recovery: Service auto-restarts if it crashes
Clean Resource Management: Proper cleanup on shutdown
Lock File: Prevents multiple instances from running
